## Addition II: VPC and private networking

**What we built.** The three servers run in their own VPC (`coinbase-300w-vpc`) with two subnets. The web and app servers sit in a **public subnet** whose route table sends internet traffic to an internet gateway. The database server sits in a **private subnet** whose route table has no route to the internet at all, only local VPC traffic and an S3 gateway endpoint. The database server has no public IP address.

**How the tiers are restricted.** Each server has its own security group, and every server-to-server rule references another security group rather than an IP range. The database accepts MySQL (port 3306) only from the app server's security group. The app accepts its API port (5000) only from the web server's security group. Only the website (port 80) is open to the internet. The app server keeps a public IP for one reason: Flask has to reach the Coinbase API over HTTPS, and a NAT gateway (about $32 a month) would have doubled the budget.

**Why.** The Milestone 2 plan committed to restricting database connections to the application tier. A database with no public address and no internet route can't be reached from outside, even if a rule were misconfigured. Patches still reach it: the S3 gateway endpoint serves Amazon Linux's package repositories over AWS's network, at no cost.

**How we verified it** (November 18, 2026):
1. `./evidence.sh query` ran Flask's own `get_all_cryptos()` on `coinbase-300w-app`. It connected to MariaDB at a private-subnet address on port 3306 and returned all 8 rows.
2. `./evidence.sh db` showed MariaDB listening on 3306 on `coinbase-300w-db`, and a request from the DB server to the Coinbase API timed out, confirming it has no internet path.
3. `./evidence.sh network` showed the private route table has no internet gateway route, and that 3306 is allowed only from `coinbase-300w-app-sg`.
4. From the internet, the app's port 5000 is unreachable, while the same API works through the website's `/api/` path.

## Frontend deployment (waiting on Jake's release)

The new frontend is a static release, so deploying it only touches the web server's document root. The `/api/` gateway lives in `/etc/nginx/default.d/`, outside the document root, so a frontend release can't overwrite it. nginx serves new files immediately, and no restart is needed.

Procedure, once Jake sends the release folder or ZIP:
1. **Review:** list the exact files and their SHA-256 hashes, and confirm no file uses localhost URLs or hard-coded IPs. All API calls should use relative `/api/...` paths.
2. **Back up:** on `coinbase-300w-web`, run `sudo tar -czf /root/html-backup-<date>.tgz -C /usr/share/nginx/html .`
3. **Get approval:** Jake confirms the file list before anything is copied.
4. **Deploy:** copy the release into `/usr/share/nginx/html` (owner `root`, mode 644). Only the web server is touched.
5. **Verify:** load http://3.145.42.74/, search BTC/Bitcoin and ETH/Ethereum, open the raw JSON, check XMR shows as unavailable, and record the hashes and time.
6. **Restore if anything breaks:** `sudo rm -rf /usr/share/nginx/html/* && sudo tar -xzf /root/html-backup-<date>.tgz -C /usr/share/nginx/html`

## Current limitations

- The website is **HTTP only**. There's no domain name or TLS certificate.
- Everything runs in **one Availability Zone** with one server per tier, so there's no failover. The database has no automated backups, and running `destroy.sh` deletes it permanently.
- The app server still needs a public IP for outbound Coinbase calls because there's no NAT gateway. Its API port is closed to the internet.
- Direct SSH from a laptop allows a single admin IP. Other team members use EC2 Instance Connect in the AWS console instead.
- The database has no `category` or `description` columns yet, and no timestamp for stored prices. Coinbase's `volume` field is 24-hour trading volume in the base currency, for example BTC, not USD.
- Public IPs change if the servers are stopped and started.
- Cost is about $1.08 a day, covered by the project's $100 Free plan credits.
